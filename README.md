# RAG Vector Search (Monorepo)

A small full-stack TypeScript monorepo that indexes a document corpus into a vector
store, lets users search it semantically, and produces grounded RAG answers with
citations back to the source documents. Search is also exposed as an MCP tool.
Access is gated by authentication and role.

## Project Description

- Ingests a corpus, chunks it, generates embeddings, and stores them locally.
- **Chat page**: ask a question in natural language and get a grounded answer with
  citations to the source chunks. If the corpus does not contain the answer, the system
  says so instead of inventing one.
- **Dashboard**: an admin-only view showing real index health, ingestion status, and
  search analytics, plus a button to trigger embedding generation.
- **MCP server**: the same search capability is exposed as an MCP tool that an MCP client
  (e.g. MCP Inspector or Claude Desktop) can call.
- **Auth**: users sign in with email + password; a regular user can search, while an
  admin can also access the dashboard and management actions. Authorization is enforced
  on the server, not only in the UI.

## Technology Stack

- Frontend: Next.js + React + Tailwind CSS
- Backend: Fastify + TypeScript
- Auth: JSON Web Tokens (jsonwebtoken) with bcrypt password hashing, users in SQLite (better-sqlite3)
- Embeddings: local Python sentence-transformers service, or a remote embedding API via EMBEDDING_API_URL
- Retrieval: cosine similarity over persisted embeddings
- Answer generation: Google Gemini (gemini-flash-latest), with an extractive fallback if no key is set or the API is unreachable
- MCP: @modelcontextprotocol/sdk over stdio
- Storage: local JSON files under data/index (chunks/embeddings); SQLite (data/app.db) for users

## Design decisions

- **Retrieval is decoupled from the LLM.** Embedding and vector search are fully local.
  The LLM is used only for the generation step; if it is unavailable, the system falls
  back to an extractive answer built from the retrieved passages, so retrieval and
  citations keep working.
- **Grounding is enforced by the prompt.** The generation prompt instructs the model to
  answer only from the numbered context passages, to say the corpus does not cover the
  topic when it doesn't, and to flag deprecated/superseded information. Citations always
  come from the retrieved chunks, never from the model.
- **Authorization is server-side.** The UI hides admin controls from regular users, but
  the backend also rejects unauthorized calls (requireAuth / requireAdmin), so the API is
  protected even when called directly.
- **Chunking is sentence-aware with a fixed size target.** Documents are split on
  sentence boundaries (`. ? !` and newlines) and greedily packed into chunks of up to
  ~2000 characters (roughly 500 tokens). This keeps sentences intact rather than cutting
  mid-thought, which improves retrieval relevance. There is no overlap, which is a
  reasonable trade-off for these well-structured markdown documents; overlap or a
  smaller chunk size would be the first thing to tune for a noisier corpus.

## Repository layout

- frontend/ - Next app with chat, dashboard, and login pages
- backend/ - Fastify backend with auth, search, embedding generation, stats, and the MCP server
- packages/shared/ - shared TypeScript types
- data/ - corpus, chunks, embeddings, and the SQLite user database (git-ignored)

## Installation

### 1. Clone

    git clone <repo-url> playable-rag-vector-search
    cd playable-rag-vector-search

### 2. Install dependencies

    cd backend
    npm install
    cd ../frontend
    npm install

### 3. Prepare the Python embedding service

    cd backend
    python -m venv .venv
    .venv\Scripts\activate       # macOS/Linux: source .venv/bin/activate
    pip install -r requirements.txt

### 4. Configure environment

    cd backend
    copy .env.example .env        # macOS/Linux: cp .env.example .env

Then edit backend/.env:

- JWT_SECRET - any long random string (used to sign login tokens).
- GEMINI_API_KEY - optional. If set, answers are generated by Gemini. If empty or
  unreachable, the system falls back to an extractive answer, so the app still works
  without a key.
- GEMINI_MODEL - defaults to gemini-flash-latest.
- EMBEDDING_API_URL - the local Python embedding service (default http://127.0.0.1:8000/embed).

### 5. Seed the database with demo users

    cd backend
    npm run seed

## Running the Application

Open three terminals.

**1. Python embedding service** (needed to embed queries and chunks):

    cd backend
    .venv\Scripts\activate
    python embedding_server.py

**2. Backend:**

    cd backend
    npm run dev

**3. Frontend:**

    cd frontend
    npm run dev

Open http://localhost:3000. You will be redirected to /login.

## API Documentation

Protected endpoints require Authorization: Bearer <token> (token from login).

### POST /api/auth/login
    { "email": "admin@demo.com", "password": "admin123" }
Returns { "token": "...", "user": { "id": 1, "email": "...", "role": "admin" } }.

### GET /api/auth/me  (auth required)
Returns the current user's profile from the token.

### POST /api/search  (auth required: any signed-in user)
    { "query": "What is the maximum file size for an AppLovin playable?", "k": 5 }
Returns query, results (top chunks with scores), composed.answer, composed.citations, and source.

### POST /api/embeddings/generate  (admin only)
Generates embeddings for all chunks in data/index/chunks.json.

### GET /api/admin/stats  (admin only)
Returns real system stats: document / chunk / embedding counts, index health,
ingestion status, and a session search counter.

### GET /health
Health check.

## MCP Server

Search is exposed as an MCP tool named search over stdio, implemented in
backend/src/mcp-server.ts. It reuses the same retrieval + grounding pipeline as the HTTP
API. The Python embedding service must be running so queries can be embedded.

Run the MCP server directly:

    cd backend
    npm run mcp

### Connect with MCP Inspector

    cd backend
    npx @modelcontextprotocol/inspector npx ts-node -r dotenv/config src/mcp-server.ts

Open the Inspector URL, click Connect, open Tools, select search, enter a query, and run
it. It returns a grounded answer plus the source chunks. I verified this end to end:
the server connects, lists the `search` tool, and a call returns a grounded answer with
its source documents (e.g. the AppLovin 5 MB file-size limit).

### Connect with Claude Desktop

The MCP server was verified with MCP Inspector (above). To use it from Claude Desktop,
add the following config (this configuration is standard but was not tested on this
machine, as Claude Desktop was not installed):

Add this to claude_desktop_config.json
(Windows: %APPDATA%\Claude\claude_desktop_config.json,
macOS: ~/Library/Application Support/Claude/claude_desktop_config.json), then restart it:

    {
      "mcpServers": {
        "rag-vector-search": {
          "command": "npx",
          "args": ["ts-node", "-r", "dotenv/config", "src/mcp-server.ts"],
          "cwd": "<absolute-path-to>/playable-rag-vector-search/backend"
        }
      }
    }

> MCP authentication (OIDC) is a listed bonus and is not implemented; the MCP tool is
> unauthenticated in this version.

## Features

Implemented:
- Monorepo with frontend, backend, and shared types
- Ingestion / chunking pipeline with persisted chunk + embedding files and ingestion status
- Semantic vector search (cosine similarity) with a low-confidence cutoff
- Grounded RAG answers via Gemini, with inline citations and an extractive fallback
- Honest "not in the corpus" behavior when nothing relevant is retrieved
- Chat page (any authenticated user)
- Admin-only dashboard with real index/ingestion stats and a search counter (in-memory,
  resets on backend restart; a persistent store would be the production choice)
- JWT authentication with admin / user roles, enforced server-side
- MCP server exposing search as a tool (verified with MCP Inspector)
- Responsive, dark-themed UI with light search-experience polish (per-source relevance bars)

Not implemented (listed bonuses):
- MCP authentication via OIDC
- Self-updating / incremental ingestion
- Live public deployment

## Deployment

This project runs locally. To deploy, I would build the frontend with next build, run
the backend as a Node service behind a reverse proxy, move the vector persistence to a
managed store such as pgvector or Qdrant, move the SQLite user store to a managed
database, and serve everything over HTTPS with secrets supplied as environment variables.
